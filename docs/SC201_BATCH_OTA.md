## 操作

1. 使用工作台顶部的账号与服务器入口登录。已有同服务器、同账号 App3 缓存时，也可沿用原离线缓存连接。
2. 停止单设备操作并断开连接，点击左侧“扫描”。在同一个蓝牙列表中勾选要升级的设备，可使用“勾选全部设备”。
3. 在原“固件文件”处选择镜像，核对“期望版本”。一个批次使用同一份镜像；程序从镜像的准确型号标记识别 SC200-D、SC201-S 或 SC202-S，并在每台设备连接后再次核对型号和 SN。原固件若明确包含多个兼容型号标记，可将这些型号放入同一批次；每台仍按其认证后的实际型号申请升级准入。
4. 设置“同时升级”：默认 2 台，可选 1～4 台；1 台为顺序执行。“确认后立即推进”默认开启；取消勾选可对照原来的轮询推进方式。“按蓝牙 MTU 缩小固件块”和“吞吐优先（Windows 11）”默认关闭；当前 SC200-D 双台对照实测中，关闭更快。日常升级关闭窗口底部的“详细日志”。点击“开始批量升级”。
5. 查看每台设备的阶段、进度、传输速度、“传输 / 总耗时”、当前/目标版本和结果。传输计时从查询升级目标开始，到发送重启结束；总计时还包含连接、认证和重启后验版。传输 100% 后仍要等待重启、重新认证和版本确认，只有验版通过才显示“成功（已验版）”。
6. 完成后可导出 CSV。结果不包含服务器 Authorization、访问 PSK 或根密钥。

实际并发能力需要在所用电脑、蓝牙适配器和设备上验证。连接不稳定时可将并发数调低。

## v2.9.4 确认后立即推进与分段计时

原有状态机每次 poll 推进一步；收到 ACK 后切换到等待存储报告，确认存储后切换到准备下一块，下一块排队后还需要 node poll 才提交到传输层。事件回调已经触发一次轮询，但若就绪状态仍未走完，部分步骤会留到下一次 10 ms 定时轮询。

新增的“确认后立即推进”在原通信线程内重复执行完整的、带连接代次检查的 owner poll。仅当同一 OTA 传输的公开状态实际改变时继续；状态未改变即停止，每次外部调用最多 8 次。进入重启、取消或终态、连接代次改变时停止；保留原 10 ms 定时器作为等待期间的轮询。原单设备流程默认沿用原推进方式；这项开关控制批量任务。

该修改沿用冻结库的公开状态查询与 poll，不写库内部状态；每块仍等待匹配 ACK 和存储报告，仍校验整份 CRC，并在重启后重新认证、验版。每台仍只有一个未完成的 WinRT 写操作。

本次隔离回归中，相同 ATT 244、216 字节块的两台模拟设备，“确认到齐到下一块排队”的平均空档在原推进方式下为 10.536 / 9.273 ms，立即推进下为 0.027 / 0.025 ms；单次最多实际使用 4 步，未达到 8 步上限。这是模拟传输中的本机调度指标，现场无线吞吐和完整升级耗时仍待验收。

另外通过真实 TLS 连接，让 ACK 正常到达并暂扣加密存储报告：报告未放行时保持第 1 块等待；放行后可完整升级、重启并验版。另一个用例在该等待期间取消一台，另一台仍正常验版，已取消设备没有执行重启。相关用例使用异步忙传输层，验收不会假定数据一提交就已经发送完。

每个连接新增 `[ota-timing]`，每 128 块输出累计指标，数据完成和结束时也保留汇总；不输出原始帧、授权或密钥：

| 指标 | 计时边界 |
| --- | --- |
| `queue_ack_avg_ms` | 数据块成功排入原生库，到收到该块匹配的链路 ACK |
| `queue_store_avg_ms` | 同一排队点，到原生库接受该块的存储报告 |
| `confirmed_next_avg_ms` / `confirmed_next_max_ms` | ACK 与存储报告均已到齐，到下一块成功排队的本机等待 |
| `next_samples` / `cycle_avg_ms` | 完整相邻块样本数 / 相邻两次排队的间隔 |
| `store_before_ack` | 存储报告先于 ACK 被观察到的次数，避免把逆序当成负耗时 |
| `retries` / `incomplete` | 重新提交次数 / 未取得完整匹配确认的尝试，不混入完整样本均值 |
| `extra_passes` / `max_passes` | 额外推进次数 / 单次外部轮询实际使用的最大步数 |

两项 `queue_*` 共享起点，不能相加；它们不是空口抓包或设备 Flash 的独立计时。`confirmed_next` 可直接观察本机确认后的推进空档，但此前发送的 ACK、Windows 队列、无线调度和接收端处理仍会影响整个升级速度。

便携包为 `dist/sc201_workbench_portable_batch_ota_event_20261102.zip`。软件回归在临时目录中使用真实协议、TLS、模拟存储及重启验证；不能把模拟器的调度差异当成现场提速比例。2026-11-03 已完成下述授权实机对照，未测到整体提速；历史现场结果仍按原范围保留。

## 历史 v2.9.2 按蓝牙容量选择固件块

v2.9.1 的现场复测仍慢：最近一次双台传输日志为 461.807 / 473.225 秒。两台的 `ThroughputOptimized` 请求均返回 `Success`，随后实际连接间隔仍为 30 ms。请求被接受不表示最终达到了期望的 15 ms，也不能据此断言是电脑或设备哪一侧限制了间隔。

本版直接减少跨 ATT 的数据写入：当前 `MTU=247` 对应 `ATT payload=244`；原 216 字节固件块加上协议、加密、CRC 与 COBS 后常见约 283 字节，最坏上界 284 字节，需要两次写入。新选项按冻结库公开的长度常量计算上界，选择 4 字节对齐的 176 字节块，最大帧长为 243 字节，一次写入可装下。小 MTU、未知 MTU，或拆分减少不足以抵消增加的块确认开销时，保留原方案。一次传输开始后不修改块大小。

仅改变应用交给原生 OTA 作业的块大小，不增加未完成的 WinRT 写操作，不改变冻结库、接收端固件或协议格式。接收端仍逐块确认 Flash 存储，整份镜像仍校验 CRC，重启后仍需认证并核对版本。

以 714,180 字节镜像为例，数据块从 3,307 块增加至 4,058 块；仅数据帧所需的 ATT 写入次数预计从 6,613 次降至 4,058 次。块数增加也会增加存储报告和回执，因此这个约 39% 的数据写入次数降幅不等于整个升级耗时降幅，更不代表能让双台达到单台约 220 秒。

复测建议：固定同一镜像、设备、适配器和 USB 插口，保持并发 2 台、详细日志关闭，先比较“按蓝牙 MTU 优化固件块”开启和关闭两轮。`[ota-att]` 日志记录实际选择的块大小及每个数据帧的最大分包数；`[ble-perf] write_summary` 在每次连接关闭时汇总 Windows 写入完成和 Qt 调度耗时。它们是本机 SDK 指标，不证明无线发送完成。再单独比较“吞吐优先”开启和关闭，避免同时改变多个条件。

v2.9.2 发布前的软件验证使用实际 TLS、协议、模拟存储和重启，覆盖小 MTU、原分块及新分块；还从实际加密输出中用冻结库的公开帧接口校验大小。发布前没有现场速度验收，后续现场对照确认了减速，见上表。

## v2.9.1 吞吐优化与复测

本机已有日志中，同一份 714,180 字节镜像、同样 MTU 247 / ATT 244，单台传输约 224.7 秒，双台各约 404.0 / 406.7 秒。双台接近翻倍说明同时连接不等于无线总带宽翻倍。日志还暴露出软件开销：批量地址前缀使原详细日志过滤失效，约 4 万行包记录进入界面日志；结果表在每块进度到来时自动重算列宽。

本版做了以下修改：

- 每个升级连接在传输前请求 Windows `ThroughputOptimized`，发送重启、结束、取消或断开后释放请求。重连代次关闭时会清理事件订阅与请求对象。系统不支持或拒绝时继续使用现有参数，日志记录 `[ble-perf]` 请求状态与实际连接间隔。
- “详细日志”关闭时，跳过 OTA 传输包的诊断解码和十六进制展开；成功进度每 128 块保留一次，并保留首尾、错误、重传、身份核对、重启及验版记录。升级中切换“详细日志”会即时应用，之后启动的排队设备也会沿用。之前省去的原始包不会补回。
- 批量日志过滤支持地址前缀；结果表每 250 ms 刷新，列宽可手动调整。原 10 ms 协议轮询改为精确计时器，间隔与协议调用顺序保持原值。
- 分开统计传输时间和总时间，速度按传输时间计算。100% 后仍占用升级通道并等待原流程验版，计时显示变化不代表无线吞吐变化。

Windows 吞吐参数是偏好请求，可能被驱动或设备拒绝，也可能减少系统可同时维持的蓝牙连接数量；[微软的 OTA 使用建议](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothledevice.requestpreferredconnectionparameters?view=winrt-26100)说明了这一取舍。Windows 10 自动使用原参数。若开启后连接不稳，可在下一批取消勾选并比较。

后续复测应保持同一适配器、同一 USB 插口、同一镜像和相同设备位置，一次只改变一个条件，保存结果 CSV。比较每台“传输耗时秒”、整个批次完成时间和日志中的实际连接间隔。v2.9.1 的吞吐请求没有使双台达到单台约 220 秒；后续现场对照见上表。

## 绑定、重试与取消

没有可用授权或需要重新绑定的设备显示“需要绑定”，其他设备继续执行。程序不会自动认领这些设备。先在设备上打开绑定窗口，在结果表中选中对应行，再点击“绑定窗口已打开，继续选中设备”，才会沿用原 AppController 的认领和 App3 认证流程。

“重试未成功设备”会为未成功的设备开始新批次；成功设备不重复升级。开始新批次或重试会替换当前结果表，需要保留结果时先导出 CSV。设备的原有资料、账号缓存和通信日志沿用原工作台。

“取消选中任务”仅停止结果表中选中的任务。“停止全部”会取消尚未开始的排队设备，并向运行任务请求取消。若原 OTA 已进入不可中断的重启提交阶段，程序会保留会话和通道，等待原流程给出最终结果。取消版本等待可能得到“未确认”，不能据此断定设备未收到固件。

## 会话与数据

每台设备有独立的 MlinkSession、BleLink、AppController 和 ServerBackend，取消一台的 HTTP 请求不会取消其他设备。每个通道覆盖连接、认证、传输、重启和验版的完整生命周期。

批量执行期间锁定原单设备操作、账号/手机上下文、工作台资料目录以及 RTT 的发送/复位入口；日志仍可查看。窗口关闭会等待运行任务收尾，可先点击“停止全部”。

沿用原 App3 权限、DIS 公开身份核对、认证设备信息、目标准入、加密传输和升级后验版。固件大小及型号标记沿用原实现；本批次记录镜像 SHA256，排队期间文件变化的设备会在升级前拒绝执行。

v2.9.4上位机集成沿用来源工程和冻结公共库，只在RTT构建目录生成工作台UI、会话诊断与Windows蓝牙适配层的副本。上述11-03设备端候选另行修改了当前显示端OTA／BLE适配代码；未改公共库。每台仍只保留一个未完成的WinRT ATT写操作，冻结协议、帧体长度和TLS参数沿用来源实现。登录凭据仅在C++进程内传递，不进入Python状态报告或导出文件。
